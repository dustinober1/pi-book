# Novel Forge v1.10.0 — Chapter Length and Working-Tree Enforcement

v1.10.0 turns two rules that were previously guidance into checks the runtime performs, and adds a way for an accepted event to tell the writer something. It changes no project schema, workflow state, or evidence content.

## Changed

- **A chapter draft is measured against its packet.** `draft-chapter` now compares the submitted chapter to the packet's `target_words`. Between 85% and 110% of target it passes silently — the same band the chapter contract compiler derives and the deterministic scene validator enforces on the guarded path. Outside that band the event applies and returns an advisory naming both counts. Below 60% or above 150% the event is rejected as a retryable `payload-validation` problem.

  Nothing compared a hand-drafted chapter to its plan before. A real session drafted 5,211 words against a 9,000-word packet and 4,089 against a 6,000-word packet; both applied clean, and the summary reported the raw word counts with no target beside them, so a book planned at 9,000 words per chapter was quietly becoming a 5,000-word-per-chapter book.

- **The project-root boundary is enforced through Git.** Every event checks its submitted paths for uncommitted changes. A dirty submitted path was written out of band — outside a guarded event. If its content differs from the submission the event is rejected, because applying it would silently discard that work. If it matches, the event applies with an advisory: the file was still unvalidated on disk in the meantime.

  `projectStateHash` cannot see any of this. It covers `PROJECT.yaml`, `BOOK.yaml`, and a fixed evidence list, and deliberately excludes `chapter-queue.yaml`, `plot-grid.yaml`, `remarkability.yaml`, and the manuscript tree — precisely the files agents stage by writing first. In the session that motivated this, a schema-invalid `chapter-queue.yaml` sat on disk for a full minute while validation failed and was repaired.

## Added

- **Advisories.** `novel_apply_event` and `novel_validate_event` return findings that do not reject the event but that the writer would otherwise never learn. They appear in the tool result text under `Report these to the writer in your summary:`, not only in structured details an agent can skip.

- **A guarded-execution disclosure that cannot be routed around.** `SKILL.md` already required an agent to say plainly when a chapter was hand-drafted instead of executed through `novel_advance_chapter_step`. The only machine text that said so lived in that tool's error — which an agent never triggers if it checks the contracts directory, finds it empty, and goes straight to `draft-chapter`. That is exactly what happened. The disclosure now comes from `draft-chapter` itself, naming the missing contract path and stating that no scene critics, no targeted repair, and no ordered acceptance ran.

- `SKILL.md` documents the chapter-length bands, states that the project-root boundary is enforced rather than requested, requires advisories to be reproduced for the writer, and requires a summary to distinguish what the tool verified from the agent's own assessment of its prose.

## Compatibility and boundaries

This release adds validation. Two classes of event that previously applied are now rejected: a `draft-chapter` more than 40% under or 50% over its packet target, and any event whose submitted path holds differing uncommitted work. Both are retryable, both name their remedy, and `target_words` remains changeable through a `plan-change` event. Nothing else about acceptance changed, and existing projects remain fully compatible.

# Novel Forge v1.8.0 — Aggregated Event Validation

v1.8.0 changes how a rejected `novel_apply_event` reports failure. It changes no project schema, workflow state, or evidence content, and every previously valid event remains valid.

## Fixed

- **A rejection now reports every validation problem at once.** `applyNovelEvent` previously threw at the first failing validation layer. Because a single event is checked in layers — required output files, YAML and schema shape, profile packet fields, cross-artifact references, remarkability, book strategy, packet windows, and historical integrity — an author agent could only discover the contract one rejection at a time, and each round burned part of a session. A submission with three independent problems now returns one rejection listing all three, numbered, so a single corrected resubmission can fix them together. A submission with exactly one problem reads exactly as it did before.
- **The retry instruction no longer contradicts the required-file rule.** The retryable instruction said "Correct only the rejected payload and resubmit once." Following it literally — resubmitting just the one corrected file — hit `book-plan event is missing its required output file`, because an event is validated as a complete set. The instruction now says to resubmit the complete required file set with every listed problem corrected, and states that omitting an already-correct file is itself a rejection.
- **`SKILL.md` now lists the required output set for each event type**, including the two additional files a `historical-fiction` `book-plan` must carry (`historical-context.yaml`, `invention-ledger.yaml`), and states that rejections are aggregated so all listed problems should be fixed in one pass.

This fixes a real failure mode: a single historical-fiction book-planning session hit eight consecutive rejections — remarkability schema, missing required outputs, research-ledger schema twice, missing required output twice, historical-fiction profile packet fields, and reference validation — and never applied the plan. Two of those eight were caused directly by following the tool's own retry instruction.

## Compatibility and boundaries

Validation strictness is unchanged: the same events are accepted and the same events are rejected. Only the reporting changed. Structural pre-checks that make later checks meaningless — wrong stage, stale stage, stale project hash, duplicate paths, and allowlist violations — still stop immediately rather than aggregating, and a rejection with a single problem keeps its original message verbatim.

## Upgrade

Install from the pinned `v1.8.0` tag. Existing projects remain fully compatible.

# Novel Forge v2.0.1 — Novel-Start Project Discovery Fix

The README's own quick start is:

```text
/novel-start My Novel --profile thriller --type planned-series --target-words 110000
/novel
```

run from the same shell directory, with no `cd` in between. `novel-start` creates its project one directory below the cwd it was run from, and nothing moves the shell into it. Every command that resolves a project — `/novel`, `/novel-status`, `/novel-budget`, `/novel-plan`, `/novel-draft`, `/novel-review`, `/novel-revise`, `/novel-package`, `/novel-adopt`, `/novel-wizard`, both guarded-event tools, chapter-step, and plan-change — walked upward from cwd only, so the very next command in the documented flow failed with "No Novel Forge project found."

This did not surface in `novel-start --auto-to <gate>`, because that path sends its follow-up prompt with the project root embedded explicitly, bypassing cwd lookup. It is also why the one existing test exercising `novel-start` never caught it — it always passed `--auto-to`.

## Fixed

- `requireProjectRoot` — the single resolver behind every command and tool that needs a project — now falls back to checking the cwd's immediate subdirectories when the upward walk finds nothing, and resolves automatically when exactly one is a Novel Forge project: the precise shape of "I just ran `novel-start` here." Two or more candidates produce a named, actionable error listing every candidate instead of the generic "run `/novel-start`" message.

- This fallback is scoped to `requireProjectRoot` alone, not to the lower-level `findProjectRoot` used by the repository organizer's ancestor-nesting guard. A sibling Novel Forge project next to a directory being organized is not an ancestor of it, and must not block organizing that directory.

## Compatibility and boundaries

This is a pure discovery fix: no project schema, workflow state, event validation, or evidence content changed. A cwd that already resolved a project resolves the same project as before. A cwd with no project anywhere near it — including no sibling project — fails with the same message as before. The only behavior change is that a cwd with no project above it but exactly one Novel Forge project directly below it now resolves that project instead of failing.

## Upgrade

Install from the pinned `v2.0.1` tag.
